# B6：温度观测与告警到候选的映射（离线实现记录）

日期：2026-10-27。状态：离线实现并自测完成，尚未实盘验证。

## 问题

Phase 2 出现了 `hypothermia`（失温）。当时世界里的材料最低到 −86.5 °C，最高只有 16.9 °C。可是候选里没有任何一项是针对温度的：

- 告警只按世界汇总，看不出是哪个复制人失温，也看不出他周围有多冷。
- 挖掘候选只挑最长的一段可挖格子，不看温度。Phase 2 挖的是雪，而低温区的雪正是让复制人受冻的地方。

`hypothermia` 本身属于“初期”告警（`ONSET_ALERT_IDS`），不阻止恢复游戏，所以这一轮不改暂停/恢复逻辑。

## 做了什么

### Probe（全部为诊断字段，不进入任何命令契约或指纹）

- 每个复制人（`duplicants.by_instance_id.id_<n>`）新增 4 个字段：
  - `temperature_state`：`normal` / `hypothermic` / `hyperthermic`，与告警同源（`TemperatureMonitor`）。
  - `body_temperature_c`：体温。
  - `cell`：所在格子。
  - `cell_temperature_c`：所在格子的温度；真空格为 null。
- 每个挖掘候选格（`designations.dig.by_cell.cell_<n>`）新增 `temperature_c`。
- 读取失败时这些字段写 null，不会影响原有的优先级读取。温度每个 tick 都在变，所以没有加入挖掘格指纹，否则挖掘命令的前置条件会因为温度变化而失效。

### 候选（`agent/candidates.py`）

- `temperature_exposure(state)`：汇总当前开着的温度告警、受影响的复制人（含体温和周围温度），以及世界材料的最低和最高温度。
  - 字段为 null 表示没有观测到，空列表表示观测到了、但没有受影响的复制人。
  - 复制人的状态必须和开着的告警一致才算受影响。只有复制人状态、没有对应告警时，按状态过时处理，不映射任何候选。
- **缓解候选**：给受影响的复制人把 Dig（挖掘）优先级降 1 档。这是现有动作目录里最小的一步，挖掘是把复制人带到未经调温的低温材料前的那项工作。
  - 用的是普通的优先级构造器，契约照常绑定当前的优先级。
  - 最多 2 个，排在研究候选之后、一般的优先级候选之前。一般的优先级候选单独就能占满名额。
  - 和一般候选里 id 相同的那一项会被去重。
  - 优先级已经不高于 2 时不提供（见下面的审查修正）。
  - 只在暂停时提供，因为这类动作要求游戏处于暂停状态。
- **挖掘引导**：有温度告警时：
  - 失温时，不提供任何一格低于 `DIG_COLD_LIMIT_C` = −20 °C 的挖掘段，剩下的按最冷一格的温度从高到低排序，最暖的段排第一。
  - 过热时，不提供任何一格高于 `DIG_HOT_LIMIT_C` = 60 °C 的段，最凉的段排第一。
  - 两种告警同时出现时，按失温处理。
  - 没有温度数据的段（旧版 Probe）照常保留，排在有温度数据的段之后。
  - 没有告警时仍然挑最长的段，摘要里会附上温度范围。
- **备注**：
  - `temperature_alert:<告警>:exposed=<人数>`：有告警，并列出受影响人数。
  - `temperature_alert:<告警>:exposed_unobserved`：Probe 没有提供复制人的温度字段。
  - 游戏运行中也会给出这两条备注，但缓解候选只在暂停时提供。

- **审查修正（2026-10-27）：缓解有下限**：失温消退得慢，而暂停节奏每 0.25 个周期就会再问一次。如果不设下限，几次暂停就能把 Dig 一路降到 0（停用）。现在只有当前优先级高于 `TEMPERATURE_RELIEF_FLOOR` = 2 时才提供缓解，最多降到 2：复制人照常挖掘，只是排在其他工作之后。

### 模型看到的信息

`colony_summary` 新增 `temperature`：开着的温度告警、受影响的复制人，以及世界材料的最低和最高温度。

## 第二步：空间加热器（2026-10-27）

**为什么选加热器、不做隔热**：隔热砖要先规划出基地和低温区之间的整条边界，才能真正隔住冷量；单放一块不起作用，而现在的候选格扫描还做不了这种几何规划。空间加热器（`SpaceHeater`）放下就能让周围变暖，正好对应失温，只是需要电。

- **白名单**：Python、执行器、Probe 和契约的正则都加入了 `SpaceHeater`，新增 `can_place_space_heater` 和完工计数 `buildings.space_heater`。
- **研究由 Probe 指出**：我用游戏程序集的元数据核对过，`TechItems.GetTechFromItemID(string)` 返回 `Tech`，`Tech.ArePrerequisitesComplete()` 也存在。Probe 现在给每个白名单建筑的目录项发布 3 个诊断字段：
  - `unlocked`：是否已解锁。
  - `research_tech_id`：解锁它的技术，没有对应技术时为 null。
  - `research_prerequisites_complete`：这项技术的前置是否都已完成。

  这样不需要在代码里写死技术树。我没法从程序集里直接读出加热器属于哪项技术，所以由游戏在运行时回答。
- **何时提供加热器**：失温告警开着，并且已建成的加热器数量观测为 0 时，提供放置一座。先只放一座：它能不能消除失温、暖气能覆盖多远，都要实盘看过再决定要不要第二座。
- **解锁研究**：需要加热器但还没解锁时，如果前置都已完成，就提供一个 `research_<tech>` 候选，排在研究候选的最前面；游戏运行时也会提供。前置还没完成时给出备注 `unlock_research_blocked:SpaceHeater:<tech>`；这项研究已经在进行中时给出备注 `unlock_research_in_progress:...`。
- **独立供电**：一台人力发电机的输出口只能接一根电线，而加热器的耗电如果并进电解器那条线，会超出一台发电机的出力。所以：
  - Probe 的电力连线改为按组分配：编号最小、输出口空闲的发电机供氧气那一组（电解器和液体泵），下一台空闲的发电机供最近的一座未接电的加热器。
  - 需要的发电机数量 = 已建成电解器（有则 1 台）+ 已建成加热器（有则 1 台）。已建成的发电机少于这个数时，才提供人力发电机。
  - “电力连线要等泵建好”那条规则只约束通往电解器的连线，加热器自己的连线不受影响。
- **自测**：新增 `scripts/test_space_heater.py`，9 个用例：
  - 加热器的提供条件；
  - 4 处白名单一致；
  - 解锁研究：排在第一、游戏运行时也提供、前置未完成或研究已在进行时只给备注、不需要时不提供；
  - 每组各配一台发电机；
  - 加热器连线不等泵。

## 只能实盘确认

1. `TemperatureMonitor.IsHypothermic()` 与复制人身上 `hypothermia` 状态的对应关系：这和告警读取用的是同一个调用，按理一致。
2. −20 °C 和 60 °C 这两个界限是第一版的经验值。要对照实盘看：有告警时，被扣下的挖掘段多不多，会不会在冷地图上扣光所有挖掘。
3. 降低 Dig 优先级能不能真的让失温消失，要看复制人降低挖掘后是否回到基地。如果效果不明显，下一步考虑建筑类动作，比如空间加热器或隔热砖。
4. `Grid.PosToCell(identity)` 取的是复制人脚下的格子；复制人头部所在格的温度可能不同。
5. 性能：每个复制人多 4 次读取，每个挖掘格多 1 次读取，开销可以忽略，但要在 `metrics` 里确认。
6. 加热器：`research_tech_id` 实际报出的是哪项技术，它的前置是否已完成。
7. 候选格扫描给加热器挑的位置，离复制人活动的区域有多远；放远了就暖不到人。
8. 一台人力发电机能否带动加热器，以及有没有复制人去踩发电机。加热器的耗电以游戏里的数值为准，离线没有核对。
9. 加热器建好以后，失温要多久才会消失。
